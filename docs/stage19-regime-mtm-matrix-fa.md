# Stage 19: فیلتر رژیم، Mark-to-Market و ماتریس آزمایش

## جمع‌بندی

در این مرحله سه قابلیت پیاده‌سازی شد. نخست، فیلتر فاصلهٔ قیمت از EMA200 برحسب ATR به‌صورت پارامتر قابل‌تنظیم اضافه شد. دوم، summary آزمایش اکنون `markToMarketEquity`، سود/زیان شناور، cash balance و جزئیات پوزیشن‌های باز را گزارش می‌کند. سوم، runner ماتریسی برای ترکیب سبک‌ها، حالت‌های AI، sessionها، روزهای هفته و آستانه‌های regime اضافه شد.

هیچ broker write، live trading یا فراخوانی cTrader در این مرحله انجام نشد.

## فیلتر جدید

برای هر سیگنال Trend Breakout مقدار زیر محاسبه می‌شود:

```text
abs(close - EMA200) / ATR20
```

اگر این مقدار کمتر از آستانهٔ انتخاب‌شده باشد، candidate رد می‌شود. مقدار `0` رفتار baseline قبلی را حفظ می‌کند. مقدار آزمایشی این مرحله `0.25 ATR` است.

این فیلتر فقط به Trend Breakout اعمال می‌شود و رفتار سبک‌های دیگر را تغییر نمی‌دهد.

## نتیجهٔ آزمایش GBPUSD/4H

| شاخص | Baseline | فیلتر ۰٫۲۵ ATR | تغییر |
|---|---:|---:|---:|
| سیگنال | ۴۱ | ۴۰ | ۱ کمتر |
| معاملهٔ بسته | ۴۰ | ۳۹ | ۱ کمتر |
| برد | ۱۵ | ۱۵ | بدون تغییر |
| Win Rate | ۳۷٫۵٪ | ۳۸٫۵٪ | بهتر |
| Net PnL | ۷۸٫۴۸ | ۹۸٫۵۲ | +۲۰٫۰۴ |
| Profit Factor | ۱٫۱۴ | ۱٫۱۸ | +۰٫۰۴ |
| Max Drawdown | ۲٫۳۶٪ | ۲٫۳۶٪ | بدون تغییر |
| پوزیشن باز در پایان | ۱ | ۱ | بدون تغییر |
| Mark-to-Market Equity | ۱۰۰۹۰٫۲۴ | ۱۰۱۱۰٫۲۸ | +۲۰٫۰۴ |

این نتیجه برای ادامهٔ تحقیق امیدوارکننده است، اما یک آزمایش منفرد روی یک dataset است و نباید به‌عنوان اثبات edge تلقی شود. مرحلهٔ بعد باید همین آستانه را روی foldهای خارج از نمونه و cost stress اجرا کند.

## Mark-to-Market

موتور اجرا از قبل سود شناور را در سطح پوزیشن محاسبه می‌کرد، اما summary پژوهش آن را به‌صورت شفاف گزارش نمی‌کرد. اکنون برای هر run این فیلدها ثبت می‌شوند:

| فیلد | تعریف |
|---|---|
| `markToMarketEquity` | ارزش حساب با احتساب سود/زیان شناور پوزیشن‌های باز |
| `unrealizedPnlAtEnd` | مجموع سود/زیان شناور در آخرین کندل |
| `cashBalanceAtEnd` | موجودی پس از سود/زیان تحقق‌یافته و commission |
| `openPositionDetails` | قیمت ورود، قیمت جاری، جهت، زمان ورود و سود/زیان شناور هر پوزیشن باز |

بنابراین `endEquity` و `markToMarketEquity` برابر هستند، اما هر دو برای سازگاری و خوانایی گزارش نگه‌داری شده‌اند.

## ماتریس آزمایش قابل‌تنظیم

runner جدید `research:matrix:custom` از یک فایل JSON specification استفاده می‌کند. این specification اجازه می‌دهد موارد زیر ترکیب شوند:

| بعد آزمایش | پشتیبانی فعلی |
|---|---|
| سبک‌ها | چند `StrategyVariantId` در یک run |
| حالت AI | `OFF`، شورای قطعی و حالت‌های fail-closed موجود |
| آستانه regime | چند مقدار فاصلهٔ EMA برحسب ATR |
| session | Asia، London، New York و خارج از ساعت‌های اصلی |
| روز هفته | فهرست روزهای UTC، مثلاً دوشنبه تا جمعه |
| بازهٔ تاریخی | `startTime` و `endTime` |
| هزینه | spread و commission قابل تنظیم |
| چند dataset | فهرست datasetهای هم‌فرمت در spec |
| چند تایم‌فریم | با ارائهٔ dataset جداگانه برای هر تایم‌فریم |

نمونهٔ spec مرحلهٔ حاضر در این مسیر قرار دارد:

```text
data/runs/regime-matrix-spec-20260910.json
```

برای جلوگیری از انفجار تعداد اجراها، runner تعداد ترکیب‌ها را در خروجی ثبت می‌کند و هیچ حالت live یا broker را فعال نمی‌کند.

## وضعیت AI آنلاین و آفلاین

در این مرحله مدل AI پارامترهای استراتژی را تغییر نمی‌دهد. AI فقط در مسیرهای تعریف‌شدهٔ review و با محدودیت‌های fail-closed استفاده می‌شود. اجرای ترکیب‌های آنلاین در batch بدون provider واقعی عمداً انجام نشد، چون نسبت‌دادن خروجی ساختگی به مدل باعث invalid شدن نتیجه می‌شود.

مرحلهٔ بعد برای AI باید یک ablation کنترل‌شده باشد: همان dataset، همان candidateها، همان هزینه و فقط تفاوت در prompt یا نقش agent. خروجی مجاز باید شامل `APPROVE`، `REJECT` و `INSUFFICIENT_EVIDENCE` باشد.

## محدودیت‌های باقی‌مانده

فیلتر جدید هنوز روی دادهٔ broker-match و پنجره‌های OOS مستقل آزمایش نشده است. رابط کاربری اکنون آستانهٔ EMA را برای ماتریس داخل Research Desk دریافت می‌کند، اما انتخاب‌های پیچیده‌تر مانند چند dataset مستقل و prompt versioning هنوز از طریق runner JSON انجام می‌شوند و باید در مرحلهٔ UI بعدی اضافه شوند.

Paper Trading فعلی همچنان paper محلی و read-only است. اتصال به Demo cTrader و اجرای Paper-Forward واقعی هنوز به credential و preflight موفق نیاز دارد.

## نتیجه و گام بعد

فیلتر `0.25 ATR` در آزمایش فعلی تعداد معامله را کمی کاهش داد و Net PnL و Profit Factor را بهتر کرد. این نتیجه به‌اندازه‌ای امیدوارکننده است که وارد OOS محدود و cost stress شود، اما برای انتخاب نهایی کافی نیست.

گام بعدی پیشنهادی، اجرای همین مقایسه روی foldهای OOS موجود و سپس cost stress است. پس از آن می‌توان فیلتر regime را با یک روش خروج پویا مقایسه کرد؛ تغییر هم‌زمان چند پارامتر ممنوع است.
